# 0015 manual production cutover runbook

**Archived cutover procedure.** The operator reports that the production 0015 cutover completed successfully. This document preserves the steps and abort rules used to plan it; do not run 0015 again. It is not a live record of the current Vercel flag, WAF, or deployment state.

At the time this procedure was drafted, the Phase 1 application commit was `c4311083eba92a5f0c3cf9ef648f1c3a1f38f062` and `OPERATIONS_0015_ENABLED` was absent/OFF. Phase 2 reported 17 bookings, 3 preorders, 16 notes, 16 service visits, 107 audit logs, zero conversion links, zero blockers, and zero partial 0015 objects. The paused baseline subsequently recorded those five counts and the row checksums in [`0015_note_soft_delete_and_booking_return_verification_summary.sql`](0015_note_soft_delete_and_booking_return_verification_summary.sql).

After migration, the consolidated verification initially counted all 16 notes as marked because its `deleted_by` JSONB `->` test treated JSON `null` as non-SQL-NULL. A direct read-only diagnostic found `deleted_at_not_null=0`, `deleted_by_not_null=0`, `both_marked=0`, `both_null=16`, and `mismatched_pair=0`. The consolidated verification now uses direct column null checks. The supplied paused conversion and note-owner edge checksums are unavailable in this archive, so their consolidated comparison rows remain `WARNING` and require the saved operator output for a direct comparison.

## Preconditions and people

- Name one operator to control Supabase SQL Editor and one to control Vercel. Keep a shared incident log with times, deployment IDs, SQL Editor errors, and exported query results. Use the same Supabase project throughout.
- Identify an intentionally eligible booking for the return smoke test before the pause, with owner approval. It must have zero visits, `advance=0`, `final_paid=0`, and all three completion flags false. Do not return an arbitrary customer booking. Identify a controlled note/booking for the note test. If either safe test subject is unavailable, do not claim the corresponding smoke test passed; decide before cutover whether to postpone.
- Confirm every writer of this database is known. The Vercel rule below pauses this project's HTTP write routes; it does not block a direct PostgreSQL client, Supabase SQL Editor, Data API, another project, or an already in-flight request. Pause or exclude any such writer separately. Freeze deployments other than redeploying the exact commit.
- Confirm the SQL Editor session runs as the existing owner of `bookings`, `pre_bookings`, and `booking_notes`. Resolve the `gas_app_runtime`/actual `DATABASE_URL` identity and audit INSERT/RLS warning before enabling note deletion. A SQL Editor `postgres` result alone does not prove application privileges.
- Reserve a maintenance window for **writes**, not for the whole site. Pages and GET APIs stay available; the login page loads but submitting the login form is blocked because it writes a session. Authenticate the operator before the pause and ensure the session will last through verification. Budget 30–60 minutes for manual checks and deployment; keep the pause until every gate passes, regardless of elapsed time.

## Temporary write pause without app code changes

The deployed app has no maintenance switch or middleware. Its business-record mutations are `POST`, `PATCH`, and `DELETE` routes under `/api/bookings`, `/api/preorders`, `/api/preorder`, `/api/products`, and `/api/users`; there are no server actions. Payment and service mutations live under `/api/bookings`. Public preorder intake is `/api/preorder`. Login and signout POSTs also write `login_sessions`, so the broad method rule blocks them. The login page still loads, but login submission will not work during the pause.

In the Vercel project's **Firewall → Custom Rules**, prepare one temporary rule with **no persistent deny duration**. Match **Environment = Production** and method `POST`, `PATCH`, `PUT`, or `DELETE`; action `deny`. Do not add a hostname or path restriction. `gas.ecoauto.app` is not the only reachable production URL: the project's public `green-engine-gas-service.vercel.app` alias also serves the application, and generated deployment URLs may exist. A rule limited to the custom hostname is not a reliable write pause. Confirm the rule applies to every production deployment URL before continuing.

At the start of the window, publish **only this deny rule**. There is **no bypass during migration or verification**. Send harmless invalid-body/invalid-ID requests for each mutation route family to both the custom domain and the public Vercel alias; every probe must be attributed to the **deny rule** in Firewall traffic, with no corresponding Function invocation. Verify `/` and `/login` return 200 and authenticated GETs work. A bare 403 is insufficient evidence because application authorization can also return 403. Wait for in-flight writes to drain; inspect recent function activity and repeat the paused baseline if counts move. If the rule cannot be published, matched, or shown to cover every production URL and every writer, **STOP before 0015**.

Probe these route families with an empty/invalid body or nonexistent numeric ID. Use the same WAF deny condition for all of them; the expected proof is a matching Firewall deny event **before** application execution, not a particular HTTP status alone. Never send a valid production mutation as a probe.

| Route family | Harmless method/path probe |
| --- | --- |
| Booking creation | `POST /api/bookings` |
| Public and staff preorder creation | `POST /api/preorder`, `POST /api/preorders` |
| Preorder update/conversion | `PATCH /api/preorders/0`, `POST /api/preorders/0` |
| Note creation/deletion | `POST /api/bookings/0/notes`, `DELETE /api/bookings/0/notes` |
| Payment/reschedule/booking deletion | `PATCH /api/bookings/0`, `DELETE /api/bookings/0` |
| Service progress/visit | `PATCH /api/bookings/0/process` |
| Return operation | `POST /api/bookings/0/return-to-preorder` |
| Product/user workflow | `POST /api/products`, `PATCH /api/products/0`, `DELETE /api/products/0`, `POST /api/users`, `PATCH /api/users/0` |
| Login/session write | `POST /api/auth/login` |

Read probes: `GET /` and `GET /login` must be 200; from an existing authenticated session, `GET /api/me`, `/api/bookings`, `/api/preorders`, `/api/bookings/<existing-id>/notes`, and `/api/bookings/<existing-id>/process` must still work. `HEAD` and `OPTIONS` need only be **unmatched by the WAF**; application-specific status codes may differ. Repeat the mutation probes on every publicly reachable production alias and the exact deployment URL. If any reaches a Function, **STOP** and keep 0015 untouched.

Keep the deny rule active through migration, verification, flag activation and deployment. **Only after these pass**, publish a temporary first-priority custom `bypass` rule for smoke testing. Match Environment = Production, the same mutating methods, a fixed tester IP (`/32`), and a freshly generated short-lived cookie name/value. Apply it only to the controlled tester, above the deny rule. Remove the cookie and bypass before lifting the deny rule. A custom-rule bypass is distinct from Vercel's plan-limited *system bypass*.

Vercel documents [method/path/cookie/IP matching and deny/bypass actions](https://vercel.com/docs/vercel-firewall/vercel-waf/rule-configuration); [custom rules take effect without an app deployment](https://vercel.com/docs/vercel-firewall/vercel-waf/custom-rules).

## Execution sequence in Supabase SQL Editor and Vercel

1. **Begin write pause.** Publish and prove the single WAF deny rule above; pause any other database writers. Confirm in-flight requests have drained. Do not use SQL table/role changes as the pause mechanism.
2. **Confirm production baseline.** Vercel's production alias must still resolve to commit `c4311083eba92a5f0c3cf9ef648f1c3a1f38f062`, and the Production variable `OPERATIONS_0015_ENABLED` must still be absent/OFF. Check `/` 200, `/login` 200, and unauthenticated `/api/me` 403. Any mismatch: **STOP**.
3. **Paused preflight.** Run the complete single statement in [`0015_preflight_summary.sql`](0015_preflight_summary.sql) in Supabase SQL Editor. Export/save its entire four-column result table and time. The paused values, **not** the earlier 17/3/16/16/107 observations, are the baseline for verification. Save five row counts, five row checksums, conversion count/checksum, and note-owner count/checksum exactly as returned. Resolve every `WARNING` manually; `MIGRATION_DATA_GATE=PASS`, zero `BLOCKER` rows, zero partial 0015 objects, source/owner/guard checks OK are mandatory. If writes are seen after this snapshot, restart the pause verification and take a new baseline.
4. **Migration.** In a fresh SQL Editor query, paste and select the **entire** [`drizzle/0015_note_soft_delete_and_booking_return.sql`](../../drizzle/0015_note_soft_delete_and_booking_return.sql), from `BEGIN` through the final `COMMIT`, and execute it **once**. Do not run a selected fragment. Record the success/error response. Its `lock_timeout` is 10 seconds and `statement_timeout` is 60 seconds per statement. An error or ambiguous completion: **STOP**, keep flag OFF and writes paused; never rerun 0015 blindly.
5. **Verification.** Run the complete read-only [`0015_note_soft_delete_and_booking_return_verification.sql`](0015_note_soft_delete_and_booking_return_verification.sql). Supabase SQL Editor may show only one query result from a multi-statement script. While writes remain paused, **select and run each SELECT/CTE-plus-SELECT block in that same file individually** to capture all results; do not rely on the single visible final result. Export the results. Require:
   - all five new columns present, nullable, no default; all seven new constraints present/validated; three lineage FKs target the intended tables with `ON DELETE RESTRICT`;
   - four new indexes valid/ready, both unique indexes unique; note insert/update/delete/truncate guards and lineage guard enabled and attached to the expected functions; note RLS and audit INSERT effective for the **actual** app runtime role. If that role is `gas_app_runtime`, require marker-column-only UPDATE grants and the soft-delete policy. If it is a table owner, recognize that owner privileges bypass column grants/RLS unless forced, so the immutable-note trigger is the database guard;
   - five table counts and five row checksums exactly equal the **paused** baseline, along with conversion count/checksum and note-owner count/checksum; new marker/lineage values zero, duplicate/dangling links and orphan notes zero.
   Any missing result or false value is a failed verification, not a pass.
6. **Enable only after verification.** Set `OPERATIONS_0015_ENABLED=true` for Vercel **Production only**. Redeploy the exact existing compatible deployment/commit, not a newly pushed revision. Vercel applies environment changes only to a new deployment; verify the new production deployment is READY, has the same commit SHA, and has the aliases. Do not remove the WAF deny rule. [Vercel environment behavior](https://vercel.com/docs/environment-variables), [redeploying](https://vercel.com/docs/cli/redeploy).
7. **Schema-check smoke test.** From an authenticated admin/operator session, `/api/me` must expose `operations0015Enabled: true`; the note delete and return controls should appear only where authorized/eligible. A false value or 500 means the app's once-per-process schema check failed: **STOP**, keep writes paused, disable the flag for the next deployment or restore the prior flag-OFF deployment, then investigate.
8. **Controlled mutation smoke tests.** Only now publish the narrow tester bypass above the deny rule and set its temporary cookie from the preapproved fixed IP. Add one clearly labeled controlled note, delete that note through the UI after confirmation, and verify it disappears from normal history/latest preview while its audit entry retains the original note snapshot. Using the preapproved deliberately eligible booking, run return-to-preorder once; verify Booking A remains in history with cancelled status, null capacity slot and return marker; Preorder B appears with correct lineage; audit and UI refresh are correct; repeat submission is rejected. Never choose a random production booking just to complete this step. Unexpected 500, missing audit, duplicate return, or stale UI: **STOP**.
9. **Resume writes.** Clear the tester cookie; remove/disable the bypass rule and publish; then remove/disable the deny rule and publish. Confirm WAF traffic no longer denies normal write methods, public pages and authenticated reads still work, and inform staff that intake is open. Do not create an arbitrary record solely to test reopening.

## Transaction safety and abort/recovery

`0015` contains one explicit `BEGIN` and one final `COMMIT`; its normal `ALTER TABLE`, `CREATE FUNCTION/TRIGGER/INDEX`, and ACL changes are PostgreSQL transactional DDL. **If the full script is executed on one backend transaction and a statement errors before `COMMIT`, PostgreSQL aborts that transaction: earlier 0015 DDL cannot commit.** Processing of a single multi-statement query stops at the first error, so the trailing `COMMIT` may not run. The session may remain *idle in transaction (aborted)* until `ROLLBACK` on that **same session** or connection close. A `ROLLBACK` issued in a different SQL Editor session does not roll back the first session. Supabase SQL Editor does not provide a documented guarantee here that every separate Run uses the same connection; therefore do not infer rollback solely from the UI error. Inspect a fresh read-only catalog/preflight result with writes still paused. [PostgreSQL multi-statement protocol](https://www.postgresql.org/docs/current/protocol-flow.html), [ROLLBACK](https://www.postgresql.org/docs/current/sql-rollback.html), [Supabase aborted sessions](https://supabase.com/docs/guides/database/connection-management).

| Stop condition | Required response |
| --- | --- |
| Paused preflight has any `BLOCKER`, nonzero partial 0015 object count, gate not `PASS`, or unresolved runtime/owner warning | Keep flag OFF and WAF pause. Do not execute 0015. Investigate; take a fresh paused baseline only after the issue is resolved. |
| Migration SQL error, timeout, disconnect, missing success/`COMMIT` evidence, or apparent partial install | Stop; flag OFF and WAF pause remain. If the **same session** is still aborted/open, issue `ROLLBACK` there; otherwise do not assume its state. Use fresh read-only catalog checks. Never retry 0015 or manually drop objects. Escalate any committed partial state for a reviewed recovery plan. |
| Verification row loss/checksum mismatch or any missing trigger, FK, index, CHECK, policy, grant, or audit readiness | Stop before flag enable. Keep pause. Recheck paused baseline and catalogs; after `COMMIT`, `ROLLBACK` cannot undo 0015. Do not rewrite records to force a match. |
| Vercel redeployment failure, wrong SHA/alias, or application schema check false/500 | Keep WAF pause. Do not smoke test mutations. Revert Production flag to OFF and redeploy the exact compatible commit, or restore its known flag-OFF deployment; schema remains additive. Investigate before resuming writes. |
| New operation returns unexpected 500, audit is missing, note deletion appears physical, duplicate return, or UI stays stale | Stop tester activity. Remove tester cookie/bypass, keep WAF deny. Restore flag-OFF deployment if necessary. Preserve audit/log evidence and investigate. No automatic database down-migration. |

If the migration is confirmed committed, changing the Vercel flag or deployment is an **application rollback only**; it does not reverse schema 0015. Do not drop 0015 objects or restore records ad hoc. Resume writes only after the failure mode has a reviewed safe operating state.
